# Raspberry Pi (API Flask et Z-Wave)

Le module Raspberry Pi expose les commandes Z-Wave au backend selon un **contrat** précis. Les fichiers principaux sont `api_flask_zwave.py`, `zwave_client.py` et `config.py`, qui charge le fichier `.env` à la racine du projet. Le backend appelle le RPi sur le port 5000 avec les requêtes suivantes : **POST** pour l’état ON/OFF (`/api/devices/<id>/state` avec `state` true ou false), **POST** pour l’intensité (`/api/devices/<id>/brightness` avec `brightness` 0–99 et `transition`), **GET** pour lire l’état et l’intensité, et **GET** pour les données capteur (`/api/devices/<id>/sensor`). Sur un RPi Z-Wave, l’identifiant utilisé dans l’URL correspond au **node_id Z-Wave** (en base, champ `gpio_pin`). L’API Flask expose les routes racine et `/health` (pour le heartbeat), ainsi que les routes devices et nodes. Si la variable `RASPBERRY_API_KEY` est définie, le décorateur `@require_api_key` exige le header `X-API-Key` sur les routes concernées. Comme Flask est synchrone, les appels asynchrones au client Z-Wave sont exécutés via une fonction `run_async` qui crée une boucle asyncio, exécute la coroutine puis ferme le client pour éviter les erreurs de boucle d’événements. Le **client Z-Wave** (`zwave_client.py`) se connecte en priorité au WebSocket zwave-js-server (port 3000) pour les commandes d’écriture, sinon au Socket.IO de Z-Wave JS UI (port 8091). Il traduit les commandes de l’API Flask en commandes Z-Wave (setValue pour la commande 38 Multilevel Switch, lecture du Binary Sensor pour le mouvement). La détection de mouvement peut être gérée soit par un thread côté RPi qui envoie `POST /api/presence` au backend, soit par le backend qui interroge `GET /api/devices/<node_id>/sensor` et enregistre la présence puis déclenche les règles. En résumé, le flux est : Backend HTTP → Flask (port 5000) → ZWaveClient → Z-Wave JS (port 3000 ou 8091) → dongle Z-Wave → lampes et capteurs.

## WebSocket vs Socket.IO (clarification)

Deux stacks coexistent sur le RPi : **Z-Wave JS Server** (port 3000) et **Z-Wave JS UI** (port 8091).

- **WebSocket (port 3000)** : protocole zwave-js-server, utilisé en **priorité**. Il sert aux commandes d’écriture (setValue lampes), aux lectures d’état et aux refresh de capteurs. Plus fiable et moins sujet aux timeouts ; c’est le même canal que celui utilisé par Home Assistant.
- **Socket.IO (port 8091)** : interface de Z-Wave JS UI (HTTP + Socket.IO). Utilisé en **secours** lorsque le WebSocket 3000 est indisponible (service non démarré ou déploiement sans zwave-js-server). Les appels getValue/getNode via Socket.IO peuvent être plus lents ou en timeout ; le client s’appuie alors sur le cache et sur l’API HTTP de l’UI quand c’est possible.

En pratique : si zwave-js-server est à l’écoute sur le port 3000, le client privilégie toujours le WebSocket ; sinon il bascule sur Socket.IO (8091).
